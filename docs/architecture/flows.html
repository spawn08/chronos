The retry hook is special: if Model.Chat errors but the After hook clears the error and supplies a replacement ChatResponse, the agent uses it and continues — this is how transparent retries work.

StateGraph execution & checkpointing

The durable runner loop. The key durability invariant: the next node is computed before the checkpoint, and the checkpoint plus its ledger event are written together — so a crash resumes at the node that had not yet run.

engine/graph/runner.go — run loop

sequenceDiagram
    autonumber
    participant R as Runner
    participant N as Node fn
    participant TR as Tracer
    participant B as Broker
    participant S as Storage

    R->>TR: StartSpan("graph:…")
    loop while Status == Running
        alt CurrentNode is EndNode / ""
            R->>B: emit "completed"
        else step guard tripped
            R->>B: emit "error (max steps)"
            R-->>R: fail (possible cycle)
        else interrupt node (and not resuming past it)
            R->>B: emit "interrupt"
            R->>S: commit(checkpoint = this node, no event)
            R-->>R: return Status=Paused
        else executable node
            R->>TR: StartSpan("node:…")
            R->>N: callNode(ctx, node, state) [panic-recovered]
            N-->>R: newState
            R->>B: emit "node_end"
            R->>TR: EndSpan(node)
            R->>R: next = findNext(current, state)
            R->>S: commit(checkpoint = next, event "node_executed")
            R->>B: emit "edge_transition" / "completed"
        end
    end
    R->>TR: EndSpan(graph)

Atomic commit

commit() persists the checkpoint and appends the ordered ledger event in one operation, keeping state and history in sync.

Panic recovery

callNode recovers panics so a bad node fails only its own run — never the process.

Cycle guard

A step counter bounds the loop; exceeding maxSteps fails the run instead of spinning forever.

Human-in-the-loop: pause & resume

An interrupt node pauses the run and persists a checkpoint. After a human decision is recorded, Resume advances past that one interrupt exactly once; any downstream interrupt still pauses.

Durable work queue

Runs are enqueued and leased to workers. Heartbeats keep a lease alive; a worker can sleep, park for a signal, retry, or complete. Expired leases are recovered so no run is lost when a worker dies.

engine/queue/queue.go

stateDiagram-v2
    [*] --> Queued: Enqueue(run)
    Queued --> Leased: Dequeue(owner, lease)
    Leased --> Leased: Heartbeat(extend lease)
    Leased --> Sleeping: Sleep(delay, patch)
    Sleeping --> Queued: delay elapses
    Leased --> Parked: Park(waitSignal, patch)
    Parked --> Queued: signal / ReleaseAdmissionParked
    Leased --> Queued: Retry(delay, patch)
    Leased --> Done: Complete(status)
    Leased --> Queued: lease expires (orphan recovery)
    Done --> [*]

Idempotency

An idempotency key makes enqueuing the same effect twice a no-op, so retries and resumes never double-emit.

Reliable outbox

External effects are recorded in an outbox and delivered once, decoupling side effects from the run transaction.

Sandboxed execution

All four backends satisfy one interface — Execute(ctx, command, args, timeout) (*Result, error) — so the caller is identical regardless of isolation strength.

ChronosOS request & tenant isolation

Requests pass through the middleware chain, where the tenant is derived from the authenticated principal — never from client input — and is then enforced on every storage read.
