How Chronos is built

Chronos is a Go framework for agentic systems that survive restarts, scale horizontally, and stay observable. Four cooperating layers — a control plane, a durable runtime, a user-facing SDK, and pluggable storage — connected only through small interfaces.

02 Key Concepts

The ideas that define how Chronos behaves under load and failure.

Durable by default

Every graph step writes a checkpoint and an ordered ledger event in one transaction — a crash resumes exactly where it stopped.

engine/graph/runner.go

Human-in-the-loop

Interrupt nodes pause a run and persist it; a recorded approval resumes it, skipping that interrupt exactly once.

engine/graph · os/approval

Exactly-once work

Leased workers with heartbeats, orphan recovery, idempotency keys, and a reliable outbox — at-least-once effects without duplication.

engine/queue

Adapter everywhere

Backends are chosen by config and swapped with no code change — SQLite in dev, Postgres in prod, five vector stores for RAG.

storage/adapters

Safe execution

Untrusted tool code runs behind one Sandbox interface with hardened container, WASM, and Kubernetes Job backends.

sandbox/

Multi-tenant

Tenant identity rides on context, is stamped on writes and enforced on reads; cross-tenant id lookups resolve to not-found.

storage/tenant.go

Observable

The runner emits stream events and opens spans around the graph and every node; the control plane exposes them over SSE + Prometheus.

engine/stream · os/trace

Composable middleware

Hooks (retry, rate-limit, cache, cost, metrics) and guardrails wrap every model and tool call through a Chain.

engine/hooks · guardrails

Interface segregation

Relational Storage is separate from VectorStore; providers, guardrails, hooks, sandboxes are all small seams.

storage · engine

The durable runner loop. The next node is computed before the checkpoint, and checkpoint + ledger event are written together.

sequenceDiagram
    autonumber

    loop while Running
        alt interrupt node
            R->>S: commit(checkpoint = this node)
            R-->>R: Status = Paused

            R->>N: callNode (panic-recovered)
            N-->>R: newState
            R->>R: next = findNext(state)
            R->>S: commit(checkpoint = next, event)
        end
    end
    R->>TR: EndSpan(graph)

The registry consults each tool's permission; sensitive tools route through approval before executing.

flowchart TD
    M["Model returns tool_call"] --> LOOK["Registry.lookup"]
    LOOK --> PERM{Permission?}
    PERM -->|Allow| RUN["Handler(ctx, args)"]
    PERM -->|RequireApproval| REQ["Approval.Request"]
    REQ --> WAIT{Decision}
    WAIT -->|approved| RUN
    WAIT -->|denied| DENY["denied result"]
    RUN --> RES["tool result"]
    RES --> BACK["append → next Model.Chat"]
    DENY --> BACK

Chronos is an MCP client. stdio launches a subprocess; HTTP+SSE talks to a remote server, correlating responses by id.

    C->>P: "tools/list" / "tools/call"

    C->>S: GET /sse (text/event-stream)
    S-->>C: event: endpoint → /messages
    C->>S: POST /messages {id, "tools/call"}
    S-->>C: SSE message {id, result}

Runs are leased to workers; heartbeats keep the lease, and expired leases are recovered so no work is lost.

    Leased --> Sleeping: Sleep(delay)
    Sleeping --> Queued: delay elapses
    Leased --> Parked: Park(signal)
    Parked --> Queued: signal
    Leased --> Queued: Retry / lease expires
    Leased --> Done: Complete
    Done --> [*]
